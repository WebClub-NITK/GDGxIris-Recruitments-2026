## 📌 Project Overview: What is LogStream?

**LogStream** is a lightweight, single-page **Developer Observability Dashboard** that functions like a live terminal inspector. It allows developers to monitor ongoing system events, errors, and performance metrics as they happen in real-time.

Instead of a typical static app where you have to click "Refresh" to see new data, LogStream creates a continuous, live pipe between the backend server and the browser window. 

---

## 🎨 What Should the Final Output Look and Act Like?
Imagine a screen split or structured into a control panel and a visual terminal terminal box:

1. **The Control Panel:** 
   - A `Name / Client ID` input field so the user can label their session.
   - A prominent `[ ▶ Start Stream ]` button.
   - A prominent `[ 🟥 Stop Stream ]` button (disabled by default until the stream starts).

2. **The Terminal Screen:** 
   - A dark-themed, rectangular text window (resembling a command-prompt window or VS Code terminal).
   - When the user lands on the page, this terminal window is completely blank.
   - Clicking `[ ▶ Start Stream ]` makes text lines start scrolling down the screen automatically every 500 milliseconds (half a second).
   - Clicking `[ 🟥 Stop Stream ]` freezes the screen instantly.

### 📝 Example of the Live Text Outputs (Generated by Backend):

## 🛠️ Core Features to Implement (Mandatory)

### 1. The Mock Log Engine (Backend)
- Write an asynchronous data loop on your server that automatically crafts a new log text string every `500ms`.
- Each log line must contain three distinct elements:
  1. A **Log Level Tag** picked at random: `[INFO]`, `[WARN]`, or `[ERROR]`.
  2. A highly precise, real-time **Timestamp** (`HH:MM:SS.mmm`).
  3. A descriptive, dynamic **System Message** mapped logically to the chosen log tag.

### 2. Live Data Pipeline (Streaming Protocol)
- You **cannot** use short polling (meaning the frontend is strictly forbidden from using a `setInterval` loop to hit a traditional REST API endpoint over and over).
- You must use a persistent networking pipeline to push data out as soon as it is generated. Choose **one** of the following:
  - **Server-Sent Events (SSE):** Utilizing the native browser `EventSource` API (Highly Recommended for this specific task architecture).
  - **WebSockets:** Utilizing custom event emitters.

### 3. The Interactive Browser Terminal (Frontend)
- Build a single-page app displaying the control configuration and the terminal interface.
- Style the terminal layout with a dark theme (`background: #000` or `#1a1a1a`) and monospaced text to accurately mimic a system terminal.
- Implement clear toggles: when streaming is live, `Start Stream` is disabled. When streaming is stopped, `Stop Stream` is disabled.

## ⚙️ Technical Specifications & Implementation Guidelines

When building this application, ensure the system is designed to handle real-world edge cases by implementing the following technical requirements:

*   **Active Connection Management:** The backend application must actively monitor the state of each client connection. If a user terminates the stream or closes their browser tab, the server must immediately detect the disconnection. All background timers, intervals, or memory loops running for that specific session must be stopped instantly to prevent server-side resource leaks.
*   **Session Isolation Under Concurrency:** The architecture must support multiple concurrent users seamlessly. If multiple browser tabs connect to the stream at the same time, the data pipelines must remain completely isolated. Log outputs from one session must never bleed into or impact another active session.
*   **Frontend Performance Optimization:** To prevent browser lag or high memory usage when a stream runs continuously over a long duration, the user interface should not append text lines indefinitely. Implement a rolling display window on the frontend that retains only the most recent 50 to 100 log items in the document tree, dynamically removing older rows as new ones arrive.
